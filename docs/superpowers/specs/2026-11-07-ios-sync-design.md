# Синхронизация iPhone с сервером — дизайн

Дата: 2026-11-07. Владелец: КФХ Зубахин. Основа: `server/README.md` (протокол), `web/src/lib/sync.ts` (рабочий
образец клиента), приложение `TabelKFH/` (SwiftUI + SwiftData, SchemaV5).

## Зачем

Учёт ведут на хуторе, с телефонов на мобильном интернете, несколько человек сразу: владелец и помощники,
у каждого свой iPhone. Сейчас данные живут только на одном телефоне. Нужно, чтобы все телефоны и сайт
видели одно хозяйство, а связь могла пропадать на часы без потери данных.

Успех: помощник на хуторе без связи отметил часы или продажу угля; когда связь появилась, это само ушло
на сервер, и владелец видит запись на своём телефоне и на сайте. Ничего не потерялось и не задвоилось.

## Решения владельца (не менять без него)

1. Сервер — в интернете по адресу **`https://kfh.cubely.ru`**. Пока он работает **на VDS Cubely**
   (37.230.113.40, FirstVDS), потом переедет на отдельную VDS 82.146.57.87 (её ещё не удалось запустить).
   Переезд меняет только DNS-запись, приложение не пересобирается.
2. На телефоне «Марина» сейчас только тестовые данные — переносить их на сервер не нужно, хозяйство на
   сервере начинается с чистого листа.
3. **Без входа приложение не работает.** Режима «только на телефоне» больше нет.
4. **Помощники — свои iPhone, аккаунты им создаёт админ (владелец), без личных данных**: логин, пароль, роль.
   Ни почты, ни телефона, ни ФИО помощника сервер не хранит. Забытый пароль помощника меняет админ.
5. Установка остаётся через **Sideloadly** (переподпись каждого телефона раз в 7 дней). TestFlight отклонён.
6. Ставить что-либо на VDS Cubely — только после явного «выкладывай» владельца.

## Цели

- Все модули, которые уже есть на сервере (`GET /entities`: табель с часами и старыми отметками, сотрудники,
  настройки хозяйства, уголь, водители, выплаты, закрытые дни, скот, забой, агрокалькуляторы), синхронизируются
  между iPhone, другими iPhone и сайтом.
- Работа без связи: каждое действие сразу сохраняется на телефоне и встаёт в очередь; очередь уходит сама.
- Помощник видит и меняет только своё (роли сервера: `owner`, `manager`, `timesheet`, `coal`, `livestock`,
  `viewer`); модули, к которым у роли нет доступа, на главном экране не показываются.
- Владелец создаёт и отключает помощников, меняет им пароль и отзывает потерянные телефоны — на сайте и в
  настройках приложения.

## Не цели

Android, новые модули (Финансы и др.), TestFlight/App Store, push-уведомления, мгновенное обновление
у других (достаточно синхронизации раз в минуту и при открытии), перенос тестовых данных с «Марины»,
восстановление пароля помощника по почте, переезд на новую VDS (отдельная работа позже).

## Анти-цели (провал, даже если «работает»)

- Продажа, выплата, забой или операция со скотом молча потерялись или задвоились при обрыве связи.
- Помощник с ролью «табель» увидел деньги за уголь.
- После выхода помощника из аккаунта (или отзыва телефона) данные хозяйства остались на его телефоне.
- Cubely упал или стал медленнее из-за учёта фермы.

## Части работы и порядок

1. **Сервер: логины помощников** (без почты).
2. **Сайт: управление помощниками** под новый вход.
3. **Выкладка на VDS Cubely** — после «выкладывай».
4. **iPhone: вход, синхронизация, роли, выход.**
5. Сборка, установка на «Марину», проверка вживую против `kfh.cubely.ru`; затем телефоны помощников.

### 1. Сервер: логины помощников

- В `users` появляется `login` (уникальный, без учёта регистра, латиница/цифры/`-`/`_`, 3–32 символа);
  `email` у помощника пустой. Владелец по-прежнему регистрируется и входит по почте.
- `POST /members {login, password, role}` (только owner) — создаёт помощника в своём хозяйстве.
- `POST /members/{id}/password {password}` (только owner) — новый пароль; все устройства помощника
  отзываются (он входит заново).
- `PATCH /members/{id}` (роль), `DELETE /members/{id}` (отключить: все его устройства отозваны) — уже есть,
  проверить, что работают для помощников без почты. **Смена роли тоже отзывает все устройства помощника**
  (сейчас не отзывает): он входит заново, телефон стирается и получает полный набор данных новой роли.
  Иначе после понижения на телефоне остались бы чужие данные, а после повышения — не пришли бы старые записи.
- **Регистрация хозяйств закрыта** после создания хозяйства владельца: флаг в `.env` (`REGISTRATION_OPEN`,
  по умолчанию `false`; на время первой регистрации владелец включает его скриптом, как у Cubely
  `set-registration.sh`). Сайт при закрытой регистрации не показывает «Зарегистрироваться».
- `POST /auth/login` принимает в одном поле почту **или** логин (`{login, password, platform, deviceName}`;
  старое поле `email` продолжает работать).
- Приглашения по коду (`/invites`, `/auth/join`) убрать из сайта; на сервере — на усмотрение исполнителя
  (удалить или оставить неиспользуемыми), главное — один способ добавления помощника в интерфейсе.
- Ограничение частых попыток входа уже есть — распространить на вход по логину.
- Тесты на настоящей базе, как остальные серверные тесты.

### 2. Сайт

- Настройки → «Помощники»: список (логин, роль, последние устройства), «Добавить помощника» (логин, пароль,
  роль), «Сменить пароль», «Сменить роль», «Отключить». Блок кода-приглашения убрать.
- Экран входа: одно поле «Почта или логин».
- Существующие тесты синхронизации сайта не ломаются.

### 3. Выкладка на VDS Cubely

Факты о машине — `Desktop\hosting\install_plan.md`: Ubuntu, Docker 29, nginx 1.24 на хосте с certbot,
UFW (открыты 22/80/443), Postfix только на `127.0.0.1:25`, nightly restic-бэкап, DNS на Рег.ру.

- DNS: A-запись `kfh.cubely.ru → 37.230.113.40` на Рег.ру (владелец добавляет в кабинете или через API —
  как удобнее; исполнитель даёт точное значение).
- Стек `server/docker-compose.yml` (API + PostgreSQL) в своём каталоге, своя сеть и тома; API публикуется
  **только на 127.0.0.1** (порт не 4000 и не занятый Cubely), база наружу не публикуется. Помнить: опубликованные
  порты Docker обходят UFW — поэтому только 127.0.0.1.
- nginx: отдельный файл сайта `kfh.cubely.ru` → прокси на API (он же отдаёт сайт), HTTP→HTTPS, HSTS;
  сертификат certbot. **Конфиги Cubely не трогать**; перед `nginx -s reload` — `nginx -t`. Урок инцидента
  3 ноября: файлы в `sites-enabled` — ссылки, копировать нельзя.
- Ограничение памяти контейнеров (чтобы Cubely не страдал), автозапуск после перезагрузки.
- Почта для восстановления пароля владельца — через локальный Postfix (`127.0.0.1:25`, отправитель
  `noreply@cubely.ru`), если это просто; иначе код в журнале, как сейчас.
- Бэкап: **свой** systemd-таймер учёта (ночью, не в 04:15 рядом с Cubely): `pg_dump` → restic в тот же
  репозиторий S3 Cubely с отдельным тегом `kfh` (пароль и доступ — те же файлы на сервере, только чтение).
  Скрипты Cubely (`cubely-system-backup`, `check-system-backup.sh`, монитор) **не менять**. Свой скрипт
  проверки восстановления копии учёта.
- Конфликты портов: на хосте 127.0.0.1:5432 занят базой Cubely, 8080 — Wings, 4000 — API Cubely; база учёта
  наружу не публикуется вовсе, API — на свободном порту 127.0.0.1. Контейнер не видит Postfix на 127.0.0.1
  хоста — если почта не делается просто, оставить код в журнале.
- Выкладка скриптом из репозитория (как `hosting/backend/scripts/deploy.sh`), проверка
  `https://kfh.cubely.ru/health`.

### 4. iPhone

**Вход.** При запуске без сохранённого входа — экран «Почта или логин» + «Пароль». Адрес сервера зашит
(`https://kfh.cubely.ru`). Токен устройства — в Keychain; имя устройства — имя iPhone. Регистрации хозяйства
в приложении нет (хозяйство владелец создаёт на сайте). После первого входа: если на телефоне есть данные —
предложить сохранить резервную копию в «Файлы» (существующий `BackupService`), затем **стереть локальную базу**
и загрузить хозяйство с сервера (полный pull), показывая «Загрузка данных…».

**Выход** (настройки) и **отзыв устройства** (сервер ответил 401 на токен): стереть локальную базу, очередь,
курсор и токен, вернуться на экран входа. Если в очереди есть неотправленное — при ручном выходе
предупредить «N изменений ещё не отправлены. Выйти всё равно?»; при отзыве — стереть без вопроса.

**Запись изменений.** Каждое сохранение в сервисах (`HoursService`, `CoalSaleService`, `DriverService`,
`EmployeeService`, `LivestockService`, `AgroService`, настройки и т.д.) в той же транзакции SwiftData
пишет операцию в очередь: `opId` (новый на каждое действие пользователя), `entity`, `recordId`,
`baseVersion` (последняя версия, полученная с сервера), только изменённые поля. Удаление — `kind: delete`.
Одно действие пользователя = одна операция на запись. Нельзя, чтобы запись в модели и в очереди могли
разойтись (одна `save()`).

**Поля.** Имена сущностей и полей — как на сервере и в сайте (camelCase, как в моделях iPhone):
деньги — копейки (Int), даты — ISO 8601 UTC с `Z`, «день» — `YYYY-MM-DD` по часовому поясу хозяйства.
Стабильные id для записей «одна на день/хозяйство» — по правилу из `server/README.md`
(SHA-256 → UUID v8; имена `hoursMark:<employeeId>:<YYYY-MM-DD>`, `coalSettings`, `coalWorkDay:<день>`,
`deliveryLocation:<название>`, `livestockCategory:<вид>:<название>`) — **совпадение с `web/src/lib/ids.ts`
проверить тестом на общих примерах**. Источник истины формата — сайт: если поле у сайта и iPhone
называется по-разному, сначала смотреть, что пишет сайт (`web/src/pages/*.tsx`), и привести к одному.

**Настройки хозяйства.** Источник истины — сервер. Название хозяйства, руководитель, регион и **часовой
пояс** — в `farms` (`GET /me` / `PATCH /farm`, менять может только владелец), как на сайте; часовой пояс
телефона (`FarmTimeZone`) берётся с сервера после входа и при каждой синхронизации. Остальные поля
`FarmSettings` (ответственный, адрес, телефон, доп. сведения) — запись `farmSettings` со стабильным id
`stableId('farmSettings')`; `LivestockSettings` — `stableId('livestockSettings')`. Эти два имени дописать
в список стабильных id в `server/README.md` и в `web/src/lib/ids.ts`; если сайт показывает эти поля —
читать оттуда же.

**Отправка и получение** — как `SyncEngine` сайта: push очереди пачками → pull с `since` до `more: false`.
Запуск: через секунду после изменения, при запуске и возврате приложения на экран, при появлении сети
(`NWPathMonitor`), раз в минуту, пока приложение открыто, и по кнопке «Синхронизировать». Фоновой
синхронизации при закрытом приложении не нужно. Обрыв связи — операция остаётся в очереди и уходит снова
с тем же `opId`. `rejected` — операция уходит в «Не принятые» с текстом ошибки сервера (видно в настройках,
можно удалить). Применение pull: upsert/delete в SwiftData по `entity` + `id`, обновить `version`; запись,
у которой есть неотправленная операция, при pull не затирать локальными полями сервера по этим полям.

**Конфликты.** Владелец видит список в настройках («Конфликты: N»), для каждого — обе версии понятным
текстом и выбор «Оставить с сервера» / «Оставить моё» (`POST /conflicts/{id}/resolve`). Помощники видят
только число и «Обратитесь к владельцу».

**Роли.** После входа `GET /me` → роль. Главный экран показывает только доступные модули (viewer — всё,
но без кнопок изменения: формы только для просмотра или кнопки неактивны — на усмотрение исполнителя,
главное, чтобы viewer не мог поставить в очередь изменение). Владелец — в настройках «Помощники»
(как на сайте) и «Устройства» (отозвать).

**Состояние на главном экране** — одна строка, как на сайте: «Все данные синхронизированы» / «Нет связи.
Ждут отправки: N» / «Ошибка синхронизации» / «Конфликты: N».

**Резервные копии.** Сохранение копии в файл остаётся. Восстановление из файла при включённой синхронизации
сделало бы на сервере кашу — **моё решение**: восстановление из файла в приложении убрать (или оставить
только «посмотреть, что в файле» — на усмотрение исполнителя); серверные копии владельца (`/backups`) —
в настройках, как на сайте.

**Схема.** Новые модели SwiftData (SchemaV6, лёгкая миграция с V5): очередь операций, курсор `since`,
служебная `version` для синхронизируемых записей (или отдельная таблица `id → version` — на усмотрение
исполнителя), не принятые операции. Бэкап-формат не меняется (служебное в бэкап не входит).

## Мои решения (владелец может поменять)

- **Фото сотрудников не синхронизируются** — остаются на том телефоне, где их сняли. Причина: «без личных
  данных», меньше трафика на мобильном интернете. Если нужно — добавить позже через `/files`.
- Восстановление из файла бэкапа в приложении убирается (см. выше).
- Регистрация хозяйства — только на сайте.
- `viewer` в приложении — режим просмотра.
- Синхронизация только пока приложение открыто (без фоновой).
- Смена роли помощника отзывает его телефоны (входит заново, данные новой роли загружаются целиком).
- Регистрация новых хозяйств на `kfh.cubely.ru` закрыта; открывается скриптом на время.
- Настройки хозяйства и часовой пояс — с сервера, правит только владелец.
- Бэкап учёта — свой ночной таймер в тот же restic-репозиторий, скрипты Cubely не трогаются.

## Оставлено исполнителю

Разбиение кода iOS на файлы и типы, вид экранов входа/конфликтов/помощников (в стиле существующих экранов),
размер пачек push, интервалы повторов, способ хранения версий, технические детали выкладки (порт, каталоги,
лимиты памяти), миграция сервера (новый SQL-файл).

## Проверка

- Сервер и сайт: тесты на настоящей базе (как сейчас) + новые на логины помощников, смену пароля и отключение.
- iPhone (CI на macOS, без Docker): юнит-тесты движка синхронизации против подменённого сервера (URLProtocol)
  — очередь переживает обрыв, повтор с тем же `opId`, `rejected`/`conflict`/`partial`, pull с `more`, 401 →
  выход и стирание, роли скрывают модули; тест совпадения стабильных id с сайтом на общих примерах;
  миграция V5→V6.
- Вживую после выкладки: «Марина» (владелец) + сайт + второй вход помощником (можно на том же телефоне
  после выхода или в симуляторе/сайте): отметка без связи → появилась у другого; продажа угля при плохой
  связи не задвоилась; помощник «табель» не видит уголь; отключение помощника стирает данные на его телефоне.
